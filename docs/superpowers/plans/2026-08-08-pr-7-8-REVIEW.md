## The Azure wire-shape fix (PR #8's only code change) — correct

`_record_set_body` now returns `{"properties": {"ttl": …, "aRecords":
[{"ipv4Address": …}]}}` instead of the flat snake_case dict. Grounds:

- Measured live against the API: flat → `ttl=0, aRecords=[]` (silent field
  drop, call still succeeds); wire shape and explicit `RecordSet(...)` both
  round-trip.
- All five rtype branches converted consistently (`aaaaRecords/ipv6Address`,
  `cnameRecord/cname`, `ptrRecords/ptrdname`, `txtRecords/value`); the
  round-trip test passes for every branch, so each key matches the installed
  SDK's deserializer, which is generated from the same REST spec the service
  validates against.
- TXT semantics preserved: one `TxtRecord` per value, as before.
- The new test's assertions **read the fields back** rather than asserting
  key presence, so a future typo (`aRecord`) fails the test instead of
  passing vacuously.
- The failure mode analysis in the docstring matches what the reconciler
  actually did during the incident: post-apply verification re-planned and
  exited 1 with `edge 'azure-private' still drifted after apply` — the tool
  refused to report success on a broken write. That behavior is worth the
  praise the evidence gives it.

Root-cause honesty check: the claim "the 305-test offline suite could not
have caught this" is accurate — the fake client stores whatever dict it is
handed, and the two pre-existing `apply()` tests asserted the broken shape
verbatim. The new test closes exactly that class (body vs. real SDK model),
not merely this instance.

## Findings

### WR-01 (warning) — PR #7 misstates the `demo` trailing-dot defect; the defect is alive after C2

**Where:** plan `docs/superpowers/plans/2026-07-31-phase-4-cloudflare-reconciler-v2.md`,
A3 section (committed text at `9c21e10`, lines 1636–1638):

> "`demo` is one of the reconciler's `managed_keys`, so this is exactly the
> kind of drift C2 is meant to converge. Left in place deliberately: fixing
> it now would remove the test case. Issue #4 stays open and correct."

**Both claims are wrong, and the measurement proves it:**

1. *It is not drift the reconciler can converge.* `model.py:7` — CNAME
   targets are canonicalized with **trailing dots dropped** on both the truth
   side and the edge side, so `www.dwsolution.co` and `www.dwsolution.co.`
   are the same canonical value. The reconciler is structurally blind to this
   defect. Measured: after C2 fully converged (final dry-run exit 0), the
   Cloudflare edge answers `demo → www.dwsolution.co.` correctly (CNAME
   content is absolute there), while SpatiumDDI's own BIND9 still answers
   `demo → www.dwsolution.co.dwsolution.co.` (zone-file rendering treats the
   dotless value as relative and appends the origin).
2. *Fixing it would not have removed the test case.* C2's test cases were the
   two records being **absent** from the edge and the two tamper injections —
   all dot-independent. Adding the trailing dot to the truth value would have
   changed none of them.

**Consequence if left as-is:** the plan teaches a future reader that
converging C2 resolves the internal misresolution. It does not; any lab
client resolving `demo` through the SpatiumDDI resolver gets a wrong answer
today, and nothing now tracks that (issue #4, once closed, was the only
thread pointing near it).

**Fix (small, and zero edge churn — verified by the same canonicalization):**
1. Correct the paragraph on the PR #8 branch (it stacks on #7, so the merged
   state on `main` is what matters).
2. Close issue #4 as what it is — the edge-drift alert C2 resolved — and open
   a successor issue for the truth-side fix: `PUT` the Spatium `demo` value
   to `www.dwsolution.co.` (with dot). Canonicalization guarantees the
   reconciler sees no diff (dry-run stays 0, no Cloudflare write), while the
   BIND9 rendering becomes absolute. Verify with the internal dig.

### IN-01 (info) — evidence files carry CRLF and mixed dash encodings

`first-convergence.txt` / `tamper-heal.txt` contain UTF-8 em-dash sequences
alongside a stray CP1252 `0x97` byte (console-codepage bleed from the tee'd
pipeline) and CRLF endings. Harmless to git, diff, and GitHub rendering;
worth knowing only so nobody "fixes" the files and breaks the byte-identical
before/after property the ownership proof rests on. `protected-before.txt` /
`protected-after.txt` are pure ASCII — the diff evidence itself is unaffected.

### IN-02 (info) — SDK floor is looser than what was validated

`azure-mgmt-privatedns>=1.1` (pyproject) vs. 2.0.0 (uv.lock, and what the
live probe + regression test validated). The wire shape is the REST contract,
stable across SDK generations, so risk is low; raising the floor to `>=2.0`
would make the validated surface and the declared surface match. Optional.

### IN-03 (info) — hub public IP in committed evidence

`20.110.104.204` appears in `split-horizon.txt` and the PR #8 body.
Acceptable by this repo's own disclosure rules: it is a public-facing
address by design, SSH/WireGuard are NSG-gated to the home `/32`, and the
resource is ephemeral (pending teardown). Recorded here so the decision is
explicit rather than accidental — contrast CR-01 (PR #5), where the storage
account name was redacted because it named a private attack surface.
