### CR-01: Real Terraform state storage account name committed to a public repository

**File:** `docs/superpowers/plans/2026-07-31-phase-4-cloudflare-reconciler-v2.md:1649`

**Offending text:**

```
Both present in `rg-cham-tfstate` / `<stchamtfXXXXXX>`: `lab.tfstate` (3238 B)
```

**Issue:** `<stchamtfXXXXXX>` is the live Terraform remote-state storage account. This
repository is **public** (`gh repo view --json visibility` → `{"visibility":"PUBLIC"}`),
and commit `2c84acd` is the first and only occurrence of that string in the entire
history — this PR introduces the disclosure.

Three separate in-repo controls exist specifically to prevent this, and this line
defeats all of them:

1. `docs/superpowers/plans/2026-07-31-phase-2-azure-core.md:416` —
   "Add \*.tfbackend to .gitignore. **Do not commit a generated account name.**"
2. `docs/superpowers/plans/2026-07-31-phase-2-azure-core.md` §4.2 — "sensitive
   identifiers remain excluded from documentation."
3. `.github/workflows/plan.yml:122` — `echo "::add-mask::$storage_account_name"`.
   CI classifies this exact value as a secret and scrubs it from logs. The workflow
   goes out of its way to *discover* the name at runtime rather than hardcode it.

`docs/evidence/phase2/02-REVIEW.md:45` also states as a reviewed fact that no such
identifier is tracked. That statement is now false.

The internal inconsistency is on adjacent lines — line 1645, three lines above,
still redacts the same value:

```
az storage blob list --account-name <stchamtfXXXXXX> -c tfstate --auth-mode login -o table
```

**Why it matters:** Azure storage account names are globally unique DNS labels, so
this publishes the exact blob endpoints
`https://<stchamtfXXXXXX>.blob.core.windows.net/tfstate/{lab,cloudflare}.tfstate` to
anyone reading the repo. The lab state carries the approved home `/32`, subscription
id, SSH and WireGuard public keys, and every resource id in the lab. Access is
RBAC-gated (`use_azuread_auth = true`), so this is defense-in-depth loss rather than
immediate compromise — but it converts "find the account" from an unsolved problem
into a solved one, and it is permanent in git history.

**Fix (applied 2026-08-07):** replace the literal account name with the same
`<stchamtfXXXXXX>` placeholder the runbook four lines above already uses, and
say in the doc why it stays redacted. The before/after cannot be shown as a
diff here, because this review file quoted the offending line five times and
would itself have published the name — every occurrence in this document has
been redacted to the placeholder for the same reason.

Editing the line forward does not undo the disclosure. Decide explicitly between:

- **Rotate** — bootstrap a new state account, `terraform init -migrate-state` both
  roots, delete the old account; then the published name is inert; or
- **Accept and record** — if RBAC is deemed sufficient, add an ADR saying the account
  name is not treated as sensitive, and delete the three controls above so the repo
  stops contradicting itself.

Do not leave it in the current state, where the policy says one thing, CI enforces it,
and the evidence file violates it.

### CR-02: `allow_overwrite = false` is asserted as a verified safety property but is absent from `main.tf`

**File:** `docs/superpowers/plans/2026-07-31-phase-4-cloudflare-reconciler-v2.md:1576-1582`

**Offending text:**

```
Nothing here may ever delete by magnitude or by sweep. Two properties keep
that true, and both were verified against the live zone after this apply:

- Terraform manages only the two resources in its own state and has no
  `cloudflare_zone` resource, so it cannot remove a record it did not
  create. `allow_overwrite = false` means a surprise collision fails the
  apply rather than clobbering the incumbent.
```

**Issue:** `terraform/cloudflare/main.tf:37-52` sets no `allow_overwrite` on either
resource:

```hcl
resource "cloudflare_record" "www" {
  zone_id = data.cloudflare_zone.apex.id
  name    = "www"
  type    = "CNAME"
  content = var.www_public_target
  ttl     = 300
  proxied = false # keep dig-able; proxying returns Cloudflare edge IPs
}
```

Two problems compound:

1. **The property is unpinned, not configured.** The described behaviour holds only
   because the cloudflare 4.x provider defaults `allow_overwrite` to `false`.
   `main.tf:13` pins `version = "~> 4.52"`, so the default is stable *today* — but the
   guard the doc names as one of two things standing between this stack and the
   domain's live M365 mail records exists nowhere in the repository. A provider major
   bump, or anyone copying this resource block into a new root, silently loses it while
   the doc still asserts it.
2. **It cannot have been "verified against the live zone."** `allow_overwrite` is a
   plan-time provider behaviour; there is no zone-side artifact to observe. The same
   sentence covers the "no `cloudflare_zone` resource" bullet, which is likewise a
   config fact, not a live-zone fact. Only the second bullet's dry-run was an actual
   live-zone observation. The word "verified" is doing more work than the evidence
   supports, in the one paragraph a future operator will read to decide whether this
   tooling can be trusted near production mail.

**Fix:** pin the guard, then narrow the claim.

```hcl
resource "cloudflare_record" "www" {
  zone_id         = data.cloudflare_zone.apex.id
  name            = "www"
  type            = "CNAME"
  content         = var.www_public_target
  ttl             = 300
  proxied         = false # keep dig-able; proxying returns Cloudflare edge IPs
  allow_overwrite = false # explicit: a collision must fail the apply, never clobber
}

resource "cloudflare_record" "lab_marker" {
  zone_id         = data.cloudflare_zone.apex.id
  name            = "external-check"
  type            = "TXT"
  content         = "resolved-via=cloudflare-public"
  ttl             = 300
  allow_overwrite = false
}
```

And reword:

```
Two properties keep that true. The first is a property of the configuration,
readable in `main.tf`; the second was exercised against the live zone after
this apply:

- Terraform manages only the two resources in its own state and has no
  `cloudflare_zone` resource, so it cannot remove a record it did not
  create. `allow_overwrite = false` is set explicitly on both resources
  (`main.tf:37-54`), so a surprise collision fails the apply rather than
  clobbering the incumbent.
```

### WR-02: "read all 12 records" overstates the dry-run — the MX and both SRVs never entered the model

**File:** `docs/superpowers/plans/2026-07-31-phase-4-cloudflare-reconciler-v2.md:1583-1587`

**Offending text:**

```
- The reconciler's ADR-005 `managed_keys` for this edge is `demo`/CNAME and
  `reconciler-check`/TXT — disjoint from every record above, including the
  two this task creates. A dry-run against the post-apply zone read all 12
  records and reported `2 add, 0 update, 0 delete`. Zero deletes is the
  allowlist proving itself on real infrastructure rather than on a fixture.
```

**Issue:** Three separate inaccuracies, all in the direction of making the evidence
look stronger than it is.

1. **The MX and both SRVs were never read into the model.**
   `providers/cloudflare.py:338-340`:

   ```python
   rtype = str(raw["type"]).upper()
   if rtype not in SUPPORTED_RECORD_TYPES:
       continue
   ```

   `model.py:16` defines `SUPPORTED_RECORD_TYPES = frozenset({"A","AAAA","CNAME","PTR","TXT"})`.
   `MX` and `SRV` are not in it. Those three records are discarded before grouping —
   **silently**: no `self.skipped` entry, no `_warn()`, no CLI output. They are exactly
   the records lines 1572-1575 enumerate as the reason the paragraph exists
   ("`MX` → `dwsolution-co.mail.protection.outlook.com` ... and two `SRV` records").
   Whatever protected the mail exchanger during that run, it was the adapter's
   unsupported-type skip, **not** the ADR-005 allowlist.

2. **The count is wrong even for what was read.** Cloudflare models one API record per
   value, and `providers/cloudflare.py:341-345` groups by `(zone, name, rtype)`. The
   SPF `TXT` and the `MS=` verification `TXT` both sit at the apex and collapse into a
   single `CanonicalRecord` with two values. 12 zone records → 9 of supported type →
   8 canonical records. There is no execution path on which the tool observed "12".

3. **Nothing in the tool reports a record count.** `cli.py:87-107` prints only
   `SKIP`/`ADD`/`UPDATE`/`DELETE` lines, and `SKIP` covers *desired* records outside
   `managed_keys` — never actual records read from the edge. "read all 12 records" is
   an unverifiable reconstruction presented as a tool observation. Relatedly, the
   backticked quote `2 add, 0 update, 0 delete` is a partial rendition:
   `cli.py:204-205` emits
   `summary: {adds} add, {updates} update, {deletes} delete across {N} edge(s)`.
   The trimmed `across N edge(s)` is the one token that tells a reader whether the run
   actually covered this zone or was scoped to `--edge cloudflare-public`.

**Why it matters:** The conclusion is still sound —
`reconcile.py:63-70` filters `actual` down to `normalized_managed_keys` *before*
computing `to_delete`, and that filter is type-agnostic, so MX and SRV would be
protected even if they were supported. But the doc's whole purpose is to be the
artifact someone trusts later. As written, a reader auditing "is our mail safe from
this tool?" will believe the mail records were read, diffed, and deliberately spared.
They were not read at all. If a future change adds `MX`/`SRV` to
`SUPPORTED_RECORD_TYPES`, this "proof" will be cited as covering a case it never
exercised.

**Fix:**

```
- The reconciler's ADR-005 `managed_keys` for this edge is `demo`/CNAME and
  `reconciler-check`/TXT — disjoint from every record above, including the
  two this task creates (verify against `ddi-reconciler/config.toml:25-28`).
  A dry-run scoped to this edge reported
  `summary: 2 add, 0 update, 0 delete across 1 edge(s)`.
  Two independent mechanisms produced that zero, and it is worth keeping them
  apart: the `MX` and both `SRV` records never reach the diff at all, because
  `SUPPORTED_RECORD_TYPES` (`model.py:16`) excludes those types and
  `providers/cloudflare.py:338-340` skips them; the remaining eight modeled
  records are spared by the allowlist filter in `reconcile.py:63-70`, which is
  type-agnostic and would spare `MX`/`SRV` too if they were ever supported.
```

### WR-03: The stated reason `init` needs `-backend-config` is wrong, and the command omits `-reconfigure`

**File:** `docs/superpowers/plans/2026-07-31-phase-4-cloudflare-reconciler-v2.md:1557, 1563-1565`;
`terraform/cloudflare/terraform.tfvars.example:8`

**Offending text:**

```
`init` needs the explicit `-backend-config` because `plan.yml`'s static job
inits this directory with `-backend=false`, which leaves a `.terraform/`
carrying providers but no backend.
```

**Issue:** The premise is verifiable (`plan.yml:72-74` does run
`terraform -chdir="terraform/cloudflare" init -backend=false -input=false`), but the
causal claim does not hold: that job runs on an ephemeral GitHub runner and cannot
leave anything in the operator's local `.terraform/`. The two are unrelated.

The actual reason is in `main.tf:16-23` — the backend block is **partial by design**:

```hcl
backend "azurerm" {
  # storage_account_name, subscription_id, and tenant_id come from a local
  # gitignored *.tfbackend file. Credentials remain environment-sourced.
  resource_group_name = "rg-cham-tfstate"
  ...
}
```

On a virgin clone with no `.terraform/` at all, plain `terraform init` still cannot
complete non-interactively, because three required settings are absent. Publishing a
wrong reason invites the next operator to `rm -rf .terraform` and retry plain
`terraform init`, which will not work.

Second defect in the same recipe: the command omits `-reconfigure`. Both other
documented init invocations in this repo pass it —
`docs/superpowers/plans/2026-07-31-phase-2-azure-core.md:495`
(`terraform -chdir=terraform/envs/lab init -backend-config=backend.auto.tfbackend -reconfigure`)
and `plan.yml:141` (`terraform init -input=false -reconfigure ...`). Transitioning a
directory from a `-backend=false` init to a configured backend is the exact scenario
`-reconfigure` exists for, and it is the scenario this paragraph sets up.

**Fix:** in both the plan doc and `terraform.tfvars.example`:

```bash
terraform init -reconfigure -backend-config=backend.auto.tfbackend
```

and replace the explanation with:

```
`init` needs the explicit `-backend-config` because the `backend "azurerm"`
block in `main.tf` is partial by design (ADR-004): `storage_account_name`,
`subscription_id`, and `tenant_id` live in a gitignored `*.tfbackend` so no
generated account name is committed. `-reconfigure` is there because CI's
static job inits this same directory with `-backend=false`; if you have run
that locally, Terraform will otherwise refuse the backend change.
```

### IN-01: The new `spatiumddi/` ignore is unanchored and matches at any depth

**File:** `.gitignore:45`

**Offending text:**

```
spatiumddi/
```

**Issue:** Per `gitignore(5)`, a trailing slash constrains the match to directories but
does not anchor it; only a separator at the beginning or middle makes a pattern
relative to the `.gitignore`'s own directory. `spatiumddi/` therefore matches a
directory of that name at **any** depth. The comment makes the intent clear — the
root-level working clone — and this repo already has a root `spatium/` and a
`providers/spatium.py`, so a future
`ddi-reconciler/src/ddi_reconciler/spatiumddi/` client package or a
`docs/spatiumddi/` note directory is entirely plausible. It would be silently
untracked and would never appear in `git status`.

**Fix:** `/spatiumddi/`. (The file's existing `graphify-out/` and `.superpowers/`
entries share the same looseness, so this is one character of hardening on a new rule,
not a regression this PR introduced.)

### IN-02: The `.gitignore` rationale is factually wrong about how git handles an embedded clone

**File:** `.gitignore:39-42`

**Offending text:**

```
# It is a separate upstream project, kept here only so the reconciler can be
# developed against a running instance. Ignored rather than vendored: committing
# it would pull another repository's whole history into this one, and a stray
# `git add -A` is otherwise all it takes.
```

**Issue:** `spatiumddi/.git/` exists, so `git add -A` would record a **gitlink** — a
single commit SHA, with git printing its "adding embedded git repository" warning. It
would not import that repository's history or its file contents. The stated failure
mode cannot occur in the current layout, and the comment teaches the next reader a
wrong model of a git behaviour they will meet again.

The rule is still worth keeping, for a reason the comment does not give: it masks
`spatiumddi/.env`, which holds the SpatiumDDI token. (That file was already covered by
the pre-existing unanchored `.env` rule, so this is belt-and-braces, not a hole being
closed.)

**Fix:**

```
# SpatiumDDI working clone — the DDI control plane this lab reconciles against.
# It is a separate upstream project, kept here only so the reconciler can be
# developed against a running instance. Ignored because `git add -A` would
# otherwise record a gitlink to a commit nobody else can fetch — and if the
# clone is ever replaced by a plain copy without its own `.git/`, the same
# command would sweep in `spatiumddi/.env` and its API token.
```
